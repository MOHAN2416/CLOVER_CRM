## 📑 Section: Troubleshooting & System Administration Log

### 1. The Circular Dependency / Relational Design Bottleneck

* **The Issue:** In the initial schema design draft, the `Leads` table depended on a `customer_id` from the `Customers` table. However, a prospect cannot logically be assigned a customer identifier until they actually purchase a product and convert into an active customer.
* **The Resolution:** We re-architected the normalization layer by collapsing leads and customers into a unified `accounts` state-machine table. We implemented an `ENUM` field (`Lead`, `Contacted`, `Qualified`, `Active Customer`, `Inactive`) to manage the account lifecycle cleanly without breaking foreign key integrity or creating circular table dependencies.

### 2. Python-Flask Typo (`ImportError`)

* **The Issue:** Upon initiating `app.py`, the runtime environment crashed with an `ImportError: cannot import name 'render_code' from 'flask'`.
* **The Resolution:** This was a minor syntax artifact during compilation. The import statement was corrected from the non-existent `render_code` attribute to Flask's standard template-engine handler, `render_template`.

### 3. Native OS Authentication Blocking (MySQL Error 1698)

* **The Issue:** When initializing the Python connection pool, the backend threw `Error 1698 (28000): Access denied for user 'root'@'localhost'`. Modern distributions like Ubuntu 24.04 LTS protect the database `root` account by forcing it to use the system's `auth_socket` plugin (requiring explicit Linux root `sudo` privileges). Consequently, an external application script running in standard user space cannot pass raw password strings to authenticate as root.
* **The Resolution:** We bypassed the socket restriction by executing a privileged manual override. We targeted the MySQL internal user directory and forcefully modified the authentication architecture of the root account using:
```sql
ALTER USER 'root'@'localhost' IDENTIFIED WITH mysql_native_password BY 'CloverPass123!';

```


This successfully decoupled the database administrator account from the Linux kernel socket, allowing standard string-matching passwords via the Python connection pool.

### 4. Runtime Directory Crash during Safe-Mode Init

* **The Issue:** While trying to bypass a locked root state, executing `mysqld_safe --skip-grant-tables` crashed instantly with the error: `Directory '/var/run/mysqld' for UNIX socket file don't exists`. Ubuntu 24.04 cleans up temporary volatile runtime directories (`/var/run/*`) upon service stops, causing safe mode to break because its primary communication socket had no physical directory directory to bind to.
* **The Resolution:** We manually re-created the runtime directory architecture directly from the bash shell and reassigned ownership to the native database daemon group before re-firing safe mode:
```bash
sudo mkdir -p /var/run/mysqld
sudo chown mysql:mysql /var/run/mysqld

```



### 5. Asynchronous Data-Binding Delay (`Unexpected Token` Error)

* **The Issue:** The initial frontend rendering displayed a blank dashboard with `0.0%` metrics. The browser developer console flagged a `SyntaxError: Unexpected token '<' ... is not valid JSON`. This happened because the frontend JavaScript engine triggered an automated asynchronous `fetch()` request to `/api/dashboard/metrics` before the backend connection pool had fully established its handshake, resulting in the server sending back an HTML crash template instead of the expected serialized JSON payload.
* **The Resolution:** Once the database connection parameters and users were fully synchronized and stabilized in `db.py`, the backend successfully served a clean `200 OK` JSON stream. The frontend JavaScript wrapper parsed the metrics seamlessly, immediately updating the Document Object Model (DOM) to display real-time sales leaderboards.
